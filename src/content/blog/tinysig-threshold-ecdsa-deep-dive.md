TinySig is a small project with a deceptively large conceptual footprint.

The public example is only a few lines:

```python
from tinysig import ECDSASetup, ThresholdSignature

N = 3
C = 1
client_id = 1

setup = ECDSASetup(curve="P-256")
network = ThresholdSignature(N, C, setup=setup)
network.distributed_key_generation_protocol(client_id)
network.ts_prep_protocol(client_id)
network.ts_online_protocol("message", client_id)
network.print_signature(client_id)
```

But those calls hide:

- elliptic-curve ECDSA arithmetic;
- additive secret sharing in two different modular rings;
- multiplicatively masked factors;
- Paillier homomorphic encryption;
- preprocessing state;
- an emulated client/server network; and
- a non-trivial cancellation argument that recovers an ordinary ECDSA
  signature at the end.

Our historical copy was harder still: it mixed the published TinySig package,
legacy source code, Python bytecode, and a separate FastAPI/WebSocket network
experiment in one repository tree.

This chapter reconstructs the project from first principles and documents the
specific reasons our old snapshot was difficult to run.

> **Scope.** TinySig 0.1.0 is best treated as an educational/research prototype.
> This chapter is a code-reading and protocol-understanding exercise, not a
> recommendation to deploy the package for production key custody.

## 1. Which TinySig are we talking about?

The package published on PyPI is **TinySig 0.1.0**, released in December 2023.
Its project description calls it a pure-Python threshold-ECDSA implementation
built around an MPC protocol for sum-of-products computations with a
non-interactive computation phase.

The intended public API is:

```text
ECDSASetup
    ↓
ThresholdSignature
    ↓
distributed_key_generation_protocol()
    ↓
ts_prep_protocol()
    ↓
ts_online_protocol()
    ↓
print_signature()
```

That public package should be distinguished from our later local worktree,
which attempted to place threshold signing behind a real WebSocket/FastAPI
service.

## 3. Why our `runme.py` did not run cleanly

The recovered `testing/runme.py` imports:

```python
import tinysig
from tinysig import *
```

and then invokes the public API.

Running that file against the recovered directory as-is produces an import
failure because there is no normal `tinysig` source package on the import path.

Our old comments at the bottom of `runme.py` also show that we were manually
rewriting Windows `PATH` entries from Python 3.9 to Python 3.11.

So there were **two independent sources of ambiguity**:

1. **Which Python interpreter/environment was active?**
2. **Which TinySig package was actually being imported?**

The clean way to reproduce the historical package is not to patch global
`PATH`. Use an isolated environment.

For example, on Windows PowerShell:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install "tinysig==0.1.0"
python experiments/threshold-cryptography/tinysig-analysis/runme_clean.py
```

TinySig declares Python $\ge 3.10$ and its 2023 dependency set is much closer to
Python 3.10/3.11-era scientific Python than to a future interpreter with a very
different NumPy/Numba ecosystem.

CryptoCave does **not** vendor the third-party package. The companion script
simply reproduces the documented API once TinySig is installed in an isolated
environment.

## 4. What the official Python object is actually simulating

The name `Network` can initially be misleading. In the prototype, the official
execution model is an **in-memory emulator**.

Conceptually it creates:

```text
ThresholdSignature
├── nodes[]
│   ├── shares_db
│   ├── open_db
│   └── Paillier public keys
└── clients[]
    ├── shares_db
    ├── open_db
    ├── Paillier public keys
    └── Paillier private key
```

`broadcast()` writes a value into every node's in-memory database.

`send()` copies a share from each node into another in-memory object.

There are no TCP sockets, authenticated channels, distributed processes, crash
recovery rules, or real adversarial scheduling in this package layer.

That distinction is essential:

$$
\text{protocol emulation}
\neq
\text{distributed deployment}.
$$

Our later `node.py` / `server.py` work was attempting to build the second layer,
but it should not be confused with the first.

## 5. A surprising implementation detail: it is not generic $t$-of-$n$

The technical report defines threshold signatures in the usual $(t,n)$
language. The small Python prototype, however, uses ordinary **additive secret
sharing** across all configured nodes.

For a secret $a$ it creates

$$
a=a_1+a_2+\cdots+a_N\pmod q.
$$

Reconstruction sums the shares from **all $N$ nodes**.

There is no threshold parameter `t` in the public constructor:

```python
ThresholdSignature(N, C, setup=...)
```

Therefore the prototype should not be mentally modeled as a direct analogue of
our Shamir/FROST code, where any qualified subset of size $t$ can sign.

The implementation is better understood as an **N-of-N additive-sharing
emulator for the masked-factor threshold-ECDSA construction**.

That does not invalidate the algebra it demonstrates; it defines the limits of
what the code itself demonstrates.

## 6. The four arithmetic worlds

TinySig becomes easier to read if every value is assigned to the correct
algebraic domain.

### 6.1 Elliptic-curve group

ECDSA uses the point group generated by $G$:

$$
Y=xG,
\qquad
R=kG.
$$

### 6.2 Scalar field $\mathbb Z_q$

ECDSA's scalar equation lives modulo the subgroup order:

$$
s=k^{-1}(m+rx)\pmod q.
$$

### 6.3 Exponent ring $\mathbb Z_{q-1}$

TinySig also chooses a generator

$$
h\in\mathbb Z_q^*.
$$

Exponents of $h$ therefore live modulo $q-1$.
The mask exponent $\lambda$ is shared in this ring.

### 6.4 Paillier plaintext/ciphertext space

Selected mask shares are encrypted using an additively homomorphic encryption
scheme. The client owns the decryption key, while nodes hold the public key.

When reading a variable name, always ask:

> Is this an EC point, an ECDSA scalar, a mask exponent, a masked field element,
> or a Paillier ciphertext?

Many confusing labels in the prototype become understandable once this question
is asked consistently.

## 7. `ECDSASetup`: building the parameters

The prototype's `ECDSASetup` extracts:

- the curve field modulus;
- subgroup order $q$;
- base point $G$; and
- a primitive root $h$ modulo $q$.

This is already more than ordinary ECDSA needs. $h$ exists because TinySig's
masked-factor representation uses the multiplicative group $\mathbb Z_q^*$.

The recovered source obtains curve internals through a private PyCryptodome API
similar to:

```python
ECC._curves[curve]
```

That is acceptable for a research prototype but brittle engineering: names
prefixed with `_` are not stable public interfaces.

## 8. The central object: `ThresholdSignature`

`ThresholdSignature` inherits from `Network` and initializes both the signature
parameters and a Paillier keypair for each client.

The intended ownership model is:

```text
client
  owns Paillier secret key sk_HE

all signers
  know corresponding Paillier public key pk_HE
```

That ownership is a core part of the client-server security story. The signers
can homomorphically manipulate encrypted mask-share data but cannot independently
decrypt the values the client uses to authorize/finalize signing.

### Small code caveat

The recovered implementation passes `N`, `q`, and `h` to `Network.__init__`, but
not the requested client count `C`; `Network` itself defaults to one client.
The surrounding code then loops over `range(C)`.

The documented examples all use

```python
C = 1
```

which avoids the inconsistency. A reader should not infer multi-client support
has been thoroughly exercised merely because the public constructor accepts
`C`.

## 9. Understanding the database labels

The prototype stores protocol state in dictionaries using long string labels.
This is one of the main readability obstacles.

A simplified mental model is:

| Suffix / concept | Meaning |
|---|---|
| `_sh_exp` | additive share of a mask exponent in $\mathbb Z_{q-1}$ |
| `_sh_base` | additive share of a field value in $\mathbb Z_q$ |
| `_sk` | often an opened **masked factor**, not the raw ECDSA secret |
| `_pk` | corresponding public EC/group representation |
| `_enc_*` | Paillier-encrypted share/value |
| `_r` | ECDSA $r$ derived from the nonce point |

The `_sk` naming is particularly dangerous for comprehension. A label such as

```text
..._x_sk
```

may contain

$$
\langle x\rangle_{\lambda_x}
=xh^{-\lambda_x}
$$

rather than the ordinary ECDSA private key $x$.

## 10. `get_lambda()`: correlated mask material

For a label, TinySig chooses a random exponent

$$
\lambda\in\mathbb Z_{q-1}
$$

and computes

$$
h^\lambda\bmod q.
$$

It then additively shares both the exponent and related base value among the
nodes.

Schematically:

```text
lambda
├── additive exponent shares mod (q - 1)
└── shares related to h^lambda mod q
```

This preprocessed correlation is what later lets products of masked factors
have their masks corrected without revealing the underlying secrets.

## 11. DKG: what TinySig calls distributed key generation

The public call is:

```python
network.distributed_key_generation_protocol(client_id)
```

The output is conceptually a triple:

$$
\left(
\langle x\rangle_{\lambda_x},
Y=xG,
\operatorname{Enc}_{pk}(\llbracket\lambda_x\rrbracket)
\right).
$$

Here

$$
\langle x\rangle_{\lambda_x}
=xh^{-\lambda_x}\pmod q.
$$

The signers retain the masked factor and encrypted mask-share information. The
client eventually has the Paillier secret key required to decrypt authorized
combinations.

### 11.1 Key agreement intuition

The report's key-agreement subprotocol samples a random exponent $r$ and defines

$$
x=h^r\pmod q.
$$

Using shares of $\lambda_x$, the parties obtain

$$
\langle x\rangle_{\lambda_x}
=h^r h^{-\lambda_x}
$$

and also an EC point

$$
Y' = h^{\lambda_x}G.
$$

Multiplying the point by the masked scalar cancels the mask:

$$
\langle x\rangle_{\lambda_x}Y'
=
\left(xh^{-\lambda_x}\right)
\left(h^{\lambda_x}G\right)
=
xG
=Y.
$$

This gives the ordinary ECDSA public key without exposing $x$ directly.

### 11.2 This is not our Feldman/Pedersen DKG

Do not map this one-to-one onto the earlier CryptoCave DKG chapters.

Our canonical Feldman/Pedersen path studies polynomial secret sharing,
verifiable dealer contributions, complaints, qualification sets, and threshold
subsets.

TinySig's prototype is demonstrating a different client-server construction
based on additive sharing and masked factors. Calling both operations `DKG`
does not make their mechanics identical.

## 12. Signer preprocessing: preparing $k$

The first part of

```python
ts_prep_protocol(client_id)
```

creates correlated material for:

- the nonce $k$;
- a mask $\lambda_1$; and
- a mask $\lambda_2$.

The protocol constructs a masked nonce

$$
\langle k\rangle_{\lambda_k}
=kh^{-\lambda_k}.
$$

It derives the public nonce point

$$
R=kG
$$

and therefore

$$
r=x(R)\bmod q.
$$

The prototype then performs a clever local inversion.

## 13. Inverting the masked nonce

Because

$$
\langle k\rangle_{\lambda_k}
=kh^{-\lambda_k},
$$

we have

$$
\left(\langle k\rangle_{\lambda_k}\right)^{-1}
=k^{-1}h^{\lambda_k}.
$$

So TinySig can invert the **opened masked value** without opening $k$.

The source also negates the exponent-share representation, reflecting that the
mask exponent associated with the inverse changes sign.

This is one of the most important lines in the whole implementation. It is the
bridge between the nonlinear ECDSA inverse and the masked-factor MPC scheme.

## 14. The two bookkeeping exponents

TinySig's preprocessing eventually constructs two exponent combinations that
we will call

$$
\lambda_m
$$

and

$$
\lambda_{gap}.
$$

Following the recovered code's sign convention:

$$
\lambda_m
=
\lambda_1+\lambda_k
\pmod{q-1}
$$

and

$$
\lambda_{gap}
=
-\lambda_k-\lambda_2+\lambda_x
\pmod{q-1}.
$$

The exact variable names in the implementation are harder to read because
`lambda_k_inv` denotes the negated mask exponent associated with the inverted
masked nonce. Expanding the signs yields the two equations above.

These values are not arbitrary. They are chosen so **both ECDSA sum terms end
with exactly the same residual mask**.

That common residual mask is what lets the terms be added.

## 15. Client preprocessing and Paillier

The nodes encrypt their shares of the relevant exponent combinations under the
client's Paillier public key.

The client receives the encrypted pieces, decrypts them, and reconstructs:

$$
\lambda_m
$$

and

$$
\lambda_{gap}.
$$

The signers do not need the Paillier secret key.

This division of knowledge is part of the report's client-server design: the
client retains cryptographic authority needed to complete the message-dependent
signature path.

## 16. Online phase, step 1: the client masks the message

The client hashes the message to obtain

$$
m=H(M)\bmod q.
$$

It then broadcasts a masked digest equivalent to

$$
\widetilde m
=
 m h^{-(\lambda_m+\lambda_{gap})}
\pmod q.
$$

At this point the signers know the message-dependent masked value, but not a
plain collection of every secret mask used in preprocessing.

## 17. Online phase, step 2: signers evaluate the two ECDSA terms

Recall

$$
s=k^{-1}m+k^{-1}rx.
$$

The opened masked values are

$$
\langle k^{-1}\rangle
=
k^{-1}h^{\lambda_k}
$$

and

$$
\langle x\rangle
=
xh^{-\lambda_x}.
$$

The first term is formed with the $\lambda_1$ correction:

$$
T_m
=
 h^{\lambda_1}
 \left(k^{-1}h^{\lambda_k}\right)
 \left(mh^{-(\lambda_m+\lambda_{gap})}\right).
$$

Since

$$
\lambda_m=\lambda_1+\lambda_k,
$$

all but the gap mask cancels:

$$
T_m
=
k^{-1}m h^{-\lambda_{gap}}.
$$

The second term uses $\lambda_2$:

$$
T_{rx}
=
 h^{\lambda_2}
 \left(k^{-1}h^{\lambda_k}\right)
 r
 \left(xh^{-\lambda_x}\right).
$$

Its exponent is

$$
\lambda_2+\lambda_k-\lambda_x
=-\lambda_{gap},
$$

so

$$
T_{rx}
=
k^{-1}rx h^{-\lambda_{gap}}.
$$

Now both terms carry the **same multiplicative mask**.

Therefore they can be added:

$$
\widetilde s
=T_m+T_{rx}
=
\left(k^{-1}m+k^{-1}rx\right)h^{-\lambda_{gap}}
=s h^{-\lambda_{gap}}.
$$

That is the heart of TinySig.

## 18. Online phase, step 3: the client unmasks

The nodes return encrypted/additively shared contributions. The client decrypts
and reconstructs $\widetilde s$, then computes

$$
s
=
\widetilde s h^{\lambda_{gap}}
\pmod q.
$$

Substituting the previous expression:

$$
s
=
\left(sh^{-\lambda_{gap}}\right)
 h^{\lambda_{gap}}
=
s.
$$

The resulting pair

$$
(r,s)
$$

is an ordinary ECDSA signature. A verifier does not need to know TinySig was
used.

The companion

```text
experiments/threshold-cryptography/tinysig-analysis/
    masked_factor_walkthrough.py
```

checks this exact cancellation with deliberately tiny finite-field numbers and
no third-party dependencies.

## 19. Map the public API to the protocol

The five public calls can now be read much more meaningfully.

### `ECDSASetup(curve="P-256")`

Create ECDSA group/scalar parameters plus the extra multiplicative generator
$h$ needed by the mask system.

### `ThresholdSignature(N, C, setup=setup)`

Build an in-memory set of nodes/clients and generate client Paillier keys.

### `distributed_key_generation_protocol(client_id)`

Create the masked signing key state and ordinary public key $Y=xG$; encrypt the
mask-exponent shares for the client.

### `ts_prep_protocol(client_id)`

Prepare masked nonce state, compute $R$ and $r$, invert the masked nonce, derive
the two correction exponents, and let the client recover its preprocessing
masks.

### `ts_online_protocol(message, client_id)`

Mask the message digest, evaluate encrypted shares of the two ECDSA terms,
decrypt/reconstruct the common masked result, unmask it, and verify the final
ECDSA signature.

That is far more informative than reading the five function names in isolation.

## 20. Why the source feels confusing

Several engineering choices make the prototype harder to read than the report.

### 20.1 Protocol state is encoded in string labels

Instead of typed structures such as

```python
Presignature(masked_nonce=..., lambda_gap=...)
```

state is stored under long generated dictionary keys.

This makes it difficult to know which values are:

- secret shares;
- opened masked factors;
- encrypted shares;
- EC points; or
- client-only reconstructed exponents.

### 20.2 The code mixes mathematical domains

Operations modulo $q$ and modulo $q-1$ appear close together. Losing track of
which modulus applies to which variable is enough to make the derivation look
incorrect.

### 20.3 `_sk` does not always mean the real secret key

Often it means a masked secret factor. This naming is compact for the original
developers but cognitively expensive for a reader.

### 20.4 Preconditions print warnings but do not always abort

In the recovered source, `ts_prep_protocol()` catches a missing DKG-state
`KeyError`, prints a message telling the caller to run DKG first, but then
continues executing. A user can therefore encounter a later, much less obvious
failure instead of receiving one clean exception at the actual protocol
boundary.

## 21. Security and implementation caveats in TinySig 0.1.0

A deep dive should distinguish the paper's protocol ideas from limitations of a
small Python prototype.

### 21.1 Non-cryptographic Python randomness

The recovered utility layer aliases

```python
rand = random.randrange
```

from Python's `random` module.

That PRNG is not suitable for production cryptographic secrets or ECDSA nonces.
A production implementation requires a CSPRNG and a carefully designed nonce and
preprocessing lifecycle.

### 21.2 Internal ECC APIs

The setup code uses private PyCryptodome curve internals. This is convenient for
experimentation but not a stable API boundary.

### 21.3 Verification edge cases

The recovered ECDSA verification helper obtains

```python
v = int(V.x)
```

rather than explicitly reducing the x-coordinate modulo $q$, as ordinary ECDSA
verification specifies. It also performs incomplete scalar-bound checking.

These are prototype-quality details that should not be copied into production
code.

### 21.4 In-memory communication

The official prototype does not implement authenticated channels, replay
protection, transport identities, message serialization rules, persistence, or
recovery.

Those are part of a real threshold-signing system even when they are not part
of the core algebra.

### 21.5 Additive sharing means all nodes participate

As discussed earlier, the implementation does not expose a generic Shamir
threshold parameter. Losing a node is therefore different from losing one
participant in a $t$-of-$n$ FROST deployment.

### 21.6 Prototype threat model versus production engineering

The accompanying report makes phase-specific assumptions, including an honest
signer assumption in signer preprocessing and stronger signer-corruption
tolerance during later client-dependent phases. The key-agreement discussion
also distinguishes privacy from malicious correctness.

One should not compress all of that into the phrase “secure against collusion.”
The phase, corruption model, abort behavior, preprocessing erasures, and client
role matter.

## 22. Paper model versus Python prototype

It is useful to keep three layers separate.

| Layer | What it establishes |
|---|---|
| Technical report | Protocol construction, threat model, masked-factor algebra, phase structure |
| TinySig 0.1.0 | Small pure-Python emulation of the core ideas |
| Our WebSocket fork | Attempted service/orchestration layer around threshold-signing concepts |

The fork architecture image belongs to the third row, not the second.

When we originally tried to reason from all three directories at once, we were
implicitly trying to reverse-engineer three different abstraction layers at the
same time.

## 23. A cleaner way to study the project

A much better learning order is:

### Step 1 — verify ordinary ECDSA

Be comfortable with

$$
s=k^{-1}(m+rx)\pmod q.
$$

### Step 2 — understand why the naive Shamir construction fails

Read the previous CryptoCave chapter and inspect the recovered `tECDSA.py`
anti-example.

### Step 3 — understand one masked factor

Work only with

$$
\langle a\rangle_\lambda=a h^{-\lambda}.
$$

Verify multiplication and inversion identities by hand.

### Step 4 — run the dependency-free cancellation demo

```powershell
python experiments/threshold-cryptography/tinysig-analysis/masked_factor_walkthrough.py
```

Do not involve elliptic curves or Paillier yet.

### Step 5 — read the report's key agreement and signing sections

At this point the roles of $\lambda_x$, $\lambda_k$, $\lambda_1$,
$\lambda_2$, $\lambda_m$, and $\lambda_{gap}$ are much easier to follow.

### Step 6 — install TinySig in a clean Python 3.11 environment

Run the public API exactly as documented.

### Step 7 — only then inspect `tecdsa.py`

Map each method to an equation or phase instead of reading the 800-line class
top to bottom.

### Step 8 — treat the WebSocket fork as a separate systems project

Only after the in-memory protocol works should transport, identities,
persistence, and distributed orchestration be introduced.

## 26. TinySig versus FROST

Placing this chapter immediately before FROST is intentional.

| TinySig / threshold ECDSA | FROST / threshold Schnorr |
|---|---|
| Must realize $k^{-1}(m+rx)$ | Response is linear: $z=r+cx$ |
| Uses masked factors and HE/MPC | Uses Shamir interpolation directly in response |
| Significant preprocessing algebra | Two-round signing with committed nonces |
| Prototype here uses additive N-of-N sharing | FROST naturally supports threshold signer sets |
| Client has special HE/decryption role | No equivalent Paillier client role |
| Many state domains | Mostly scalar/group transcript state |

This contrast is the pedagogical payoff.

Threshold ECDSA is not difficult because elliptic curves themselves are more
complicated. FROST can use elliptic curves too. It is difficult because **the
ECDSA signing equation is algebraically hostile to local operations on secret
shares**.
